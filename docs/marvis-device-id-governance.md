# 设备身份治理：多账号部署下的设备串（qimei36）

> 面向：上游维护者、自部署用户
> 定位：讲**机制**与**运维流程**。全文不含真实设备串、真实账号标识、出口地址、部署规模，
> 示例一律用 `<24hex>` / `<8hex>` / `<ACCOUNT_KEY>` 这类占位符。

一个 MiraiHub 部署里往往跑着多个 Marvis 账号，而上游按**设备**做风控归因，不按账号。
两者一撞，就出现「一个号被拦，全部署连坐」。本文说清它为什么发生、代码里已经提供了哪些
手段、以及自部署时该按什么顺序处置。

---

## 1. 问题

### 1.1 上游按设备归因，不按账号

每次请求都会带一块 uskey（登录凭证）和一个设备串 qimei36。上游把两者绑在同一条设备记录上，
于是同一个 qimei36 下的多个账号被视为**同一台设备上的多个登录**。风控记的是设备，
不是账号 —— 处置一个账号不会让设备记录变干净。

### 1.2 典型表现

- 某个账号先被拦（403 + 业务码 `4100404`），随后**同设备串的其它账号**逐个被拦；
- **换账号无效**：被拦的是设备，顶一个没被拦过的号上去，很快也会被拦；
- **换部署有效**：新部署换了设备串，同一批账号又能跑 —— 反过来证明拦截是按设备归因的；
- 面板上看起来像「所有号都坏了」，但账号凭证本身是好的，续签、拉模型目录都正常。

### 1.3 与「配额不足」的区别

这两类故障现象很像（都是「请求发不出去」），处置完全相反，必须先分开。

| | 配额 / 额度族 | 风控族 |
| --- | --- | --- |
| 上游信号 | HTTP `402`，或平台自有的额度业务码 | `403` + 业务码 `4100404` |
| 影响的账号 | 只有额度用完的那一个 | 该设备串下的**所有**账号 |
| 换账号 | 有效 | 无效（换到同设备 = 继续被拦） |
| 换设备串 | 不必要（白白烧掉一台设备身份） | 必要，但要按 §3 的顺序 |
| 自行恢复 | 等额度窗口 / 换号 | 不会自行恢复；重试只会加深标记 |

判错方向的代价不对称：把配额问题当风控去轮换设备，等于白烧一台设备；
把风控当配额去狂换号，只会把好号一个个撞进同一个设备簇。

顺带把另外两类也分出去，别混进风控：

- `4100406` 是**内容风控**（提示词命中黑名单）—— 要改的是请求内容，换号、换设备都没用；
- `3000100` 是**上下文超限**（`400` / `413` 家族）—— 与账号、设备都无关，重发/重路由即可。

## 2. 机制

### 2.1 qimei36 的形态

- 固定 **36 位十六进制**；
- 结构 = `<24hex>` 摘要 + **固定标记** + `<8hex>` 尾段；
- 固定标记是实现里的常量 `DEVICE_MARK`（4 位十六进制），属于形态的一部分，部署方不需要改；
- 校验点：长度必须是 36，且标记位必须对得上。形态不合法**宁可本地抛错**，也不要发出去 ——
  上游会把结构异常的串记成「这个号的设备指纹坏了」。

仓库里 `admin/platform/marvis/core/qimei_table.example.json` / `qimei_pool.example.json`
给的就是这条形态，值全是 `<24hex>3000<8hex>` 这种占位写法。

### 2.2 三种来源与优先级

取设备串只有一个入口（`core/uskey.py: qimei36()`），优先级从高到低：

1. **环境变量覆盖** —— `MARVIS_QIMEI36`。只有长度等于 36 时才生效；适合单进程调试、临时验证。
2. **真值表** —— `uid -> qimei36` 映射（`core/qimei_table.json`，路径可用 `QIMEI_TABLE_PATH` 覆盖）。
   查表时账号键按去空白 + 大写归一化，与容量台账对齐。
3. **派生兜底** —— 表里没有这个账号，就按账号派生一个**结构合法**的值（见 2.3）。

真值表是可选件：文件不存在 = 空表 = 全部走派生，不会报错、不会刷警告。

### 2.3 派生兜底

派生解决的是「多账号不能共用一个设备串」，不是「伪造一台真机」：

- 算法：`sha256` 摘要（可按部署加盐），截取摘要的前后段，中间嵌固定标记，拼成合法形态；
  同一账号恒定，不同账号互不相同；
- 盐：`MARVIS_QIMEI_DEVICE_TAG`。**由部署方自己配**，同一份代码在不同部署里派生出
  互不相关的串 —— 所以「算法是公开的」不等于「能算出你的串」；
- 也可以换成 `HMAC-SHA256(盐, 账号键)`：公开的只剩接口，连摘要向量都复现不了。
  代价是已按旧口径派生的号会换串（真值表命中的号不受影响），换之前先确认没有号**只**靠派生值在跑；
- 派生值**不是**真机身份：它只保证一块 uskey 内部自洽。长期拿它当「这台设备的身份」跑，
  本身就是「只换摘要、不换源数据」的自相矛盾信号；
- 派生**不作为自动分配结果**：`assign` 只认真值表 / 新生成 / 复用，派生只作人工救灾出口
  （`--allow-derived`），且不落表、不占名额。否则「池满」会被伪装成「分配成功」。

### 2.4 容量约定：一台设备最多 2 个账号

- `MAX_OWNERS_PER_QIMEI = 2`，写在 `core/qimei_assign.py`；
- 容量权威是**池台账**（`qimei_pool.json`：`qimei -> {owners, real, created_at, last_rotated, last_used_at}`），
  不是人脑，也不是表里的重复行；
- 加载时任何一台设备的 `owners` 去重后超过 2 个 → `QimeiPoolError`；
  `marvis.install()` 在启动时调用 `validate_or_raise()`，**进程拒绝启动**；
- 这是硬约束，不是建议：带病台账宁可起不来，也不要带病跑。应急也不要临时放宽上限。

为什么是 2：共用要有明确上限才**可观测**。没有上限的共用就是本文 §1 的场景 ——
一个号出事，整簇连坐，而且事后无法判断「这台设备到底挂了几个号」。

### 2.5 名额的生命周期

- **新号入库自动分配**：挂在统一入库口（`services/accounts.py::_upsert`），
  事务提交后触发，幂等；`QIMEI_AUTO_ASSIGN=0` 可关；
- **分配顺序**：表里已有（`existing`）→ 生成新真品（`generated`）→ 复用池里名额未满的设备
  （`shared`；优先 0 owner，其次 1 owner）→ 全部满 2 个则 `QimeiCapacityError`；
- **生成失败**：打 `WARNING` 后走共用，**不静默降级成派生**；账号入库不回滚
  （不能因为设备池耗尽把账号弄丢），失败进日志与 `reconcile` 报告；
- **删号回收**：挂在 SQLAlchemy 的 `after_delete`，把账号键记进 `session.info`，
  **`after_commit` 才真正释放名额**，`after_rollback` 直接丢弃 —— 不会出现「事务回滚了、名额没了」；
  设备本身保留（`owners` 可能变 0），下次可被直接复用，不必重新生成；
- **兜底对账**：`--reconcile` 扫活跃账号补齐缺失的分配；`--prune` 回收账号已不存在的名额（默认关）。

## 3. 运维流程

### 3.1 什么时候轮换

先判维度，再动手。**轮换是状态迁移，不是重试。**

| 现象 | 判据 | 结论 |
| --- | --- | --- |
| 单账号连续 2 次 `4100404`，其它账号正常 | 账号级；同一账号换到另一台设备上验证正常 | 冷却/停用该账号，**先别动设备** |
| 同一设备串下 2 个账号先后命中 | 设备级；池台账里该设备的 `owners` 与实际一致 | 轮换**这台设备**（不是整组） |
| 全号几乎同时命中 | 先排除配额（`402`）与出口（多号共用一个出口） | 排除完再谈设备 |
| 只有一个出口下的号命中 | 出口级 | 换出口，设备不动 |
| 命中 `4100406` / `3000100` | 内容风控 / 上下文超限 | 都不是设备问题 |

单账号连续 2 次命中的口径：同一账号、同一设备串、时间上相邻的两次失败，中间没有成功请求。
偶发一次不算 —— 一次 `4100404` 也可能是那一瞬间的请求特征撞上了，立刻轮换等于自损一台设备。

### 3.2 批量轮换：先攒后写

要换的不止一台时，**先把新台账在内存/临时目录里攒齐，一次校验、一次落盘、一次部署**，
不要边算边写。

1. **算差异**：先只读演练，看清哪些设备要换、影响哪些账号：

   ~~~bash
   python3 -m admin.platform.marvis.core.qimei_assign --reconcile --dry-run --json
   ~~~

2. **攒新表**：在临时目录里生成新的 `qimei_table.json` + `qimei_pool.json`
   （用 `--state-dir <TMP_DIR>` 指过去），并保证：

   - 任何设备 `owners` ≤ 2；
   - 同一个账号不出现在两台设备上；
   - 表里的每个账号都出现在对应设备的 `owners` 里（表是读路径权威）。

3. **校验**：用同一份加载逻辑先验一遍，过不了就停在临时目录里，别碰线上：

   ~~~bash
   python3 -m admin.platform.marvis.core.qimei_assign --state-dir <TMP_DIR> --sync-pool
   ~~~

4. **一次落盘**：写盘是 `.tmp.<pid>.<rand>` + `os.replace` 的原子替换，权限 `0600`；
   顺序是**先 pool（先占名额）再 table（读路径生效）**。两步之间崩掉，最多留下
   「名额已占、表未挂」，下次加载会把 table 合并回 pool —— 容量只会更保守，不会超 2。

5. **一次部署**：把两份文件换到线上路径，**只重启一次**，然后按 §5 确认钩子与校验日志，
   再用**单个账号**验证（不是全量放量）。

6. **放量**：单账号通过后再放开。旧台账留一份做回滚（回滚也是整份换回，不要手工改一行）。

失败不写半张表的具体含义：校验发生在写之前；写是两次原子替换；加载时 table 是权威、
pool 会被归一化合并。任何一步失败都不会留下一张「表里一半是新设备、一半是旧设备」的混合态。

### 3.3 自动触发器：先分维度，再决定动作

要自动化就先分维度，否则只会把「账号级抖动」放大成「设备级轮换」。

~~~text
观测到 4100404
  ├─ 该账号在其它设备上正常？        -> 账号级：冷却/停用，不轮换
  ├─ 同设备下 ≥2 账号命中？           -> 设备级：轮换此设备（一次一台）
  ├─ 只有某个出口下的号命中？         -> 出口级：换出口
  └─ 全号同时命中 -> 先查 402 / 额度  -> 配额级：不轮换
~~~

实现建议：

- 计数按 `(账号, 设备串)` 聚合，不要只按账号；
- 设备级触发要求**同一设备下至少两个账号**命中，避免单号抖动误伤；
- 触发后**先冷却、再轮换**：立刻轮换 = 新设备身份立刻背上同一个账号的坏特征；
- 一轮只动一台设备，观察一个窗口再动下一台 —— 否则出问题无法归因。

### 3.4 反模式

| 反模式 | 后果 |
| --- | --- |
| `4100404` 时整组轮换 + 立刻重试 | 把「当前被拦」升级成「整簇不可逆标记」，新设备一起烧掉 |
| 同一设备串并发顶号 | 拦截扩散更快，日志也认不出是哪个号先坏 |
| 用派生值当长期真机身份 | 只换摘要不换源数据，自相矛盾信号 |
| 把轮换当 retry | 每次轮换都是一次成本，不是重试次数 |
| 整机镜像 / 数据卷复制后分发 | 设备身份原样带走，两边共用同一台「设备」 |
| 台账靠人手改一行 | 下次加载 table/pool 不一致，容量校验报错或者静默漂移 |

## 4. 部署清单

### 4.1 环境变量（值全部留空）

| 变量 | 作用 | 留空时 |
| --- | --- | --- |
| `MARVIS_QIMEI36` | 单进程强制指定设备串（长度必须 36） | 走真值表 / 派生 |
| `MARVIS_QIMEI_DEVICE_TAG` | 派生用的盐（部署私有的前缀串） | 用实现默认值；**建议显式配** |
| `QIMEI_TABLE_PATH` | 真值表路径 | 模块同目录 `qimei_table.json`，不存在 = 空表 |
| `QIMEI_POOL_PATH` | 容量台账路径 | 模块同目录 `qimei_pool.json`，不存在 = 空池（从表迁移） |
| `QIMEI_STATE_DIR` | 上面两个文件的所在目录（一次覆盖两者） | 模块同目录 |
| `QIMEI_DB_PATH` | 对账用的本地库路径 | 空：只按显式参数/环境变量连库，缺失时明确报错 |
| `ADMIN_DATABASE_URL` | 对账用的库连接串 | 同上 |
| `QIMEI_VALIDATE_ON_START` | `0` = 跳过启动校验 | `1`（校验，带病台账拒绝启动） |
| `QIMEI_AUTO_ASSIGN` | `0` = 关掉入库自动分配 | `1`（开启） |
| `QIMEI_GEN_CMD` | 本地生成器命令（带宿主侧参数的脚本路径） | 空：不用本地生成器 |
| `QIMEI_GEN_URL` | 外部生成器 HTTP 地址 | 空：不调外部服务 |
| `QIMEI_GEN_TIMEOUT` | 生成器超时秒数 | 30 |
| `QIMEI_GEN_SHELL` | 跑 `QIMEI_GEN_CMD` 用的 shell | `/bin/bash` |
| `QIMEI_GEN_SUDO` | `1` = 用 sudo 跑生成命令（仅在确有必要时） | 不用 |

原则：**所有部署相关路径都没有内置默认值**。想让某个能力生效，就显式给值；
不给值就是「空表 / 空池 / 不生成」，而不是悄悄指到某个固定目录。

### 4.2 真值表与容量台账

- 两份文件都**属于部署数据**，不进仓库。仓库里只有 `qimei_table.example.json` /
  `qimei_pool.example.json`，且只有 `_comment` / `_example` 元数据键；
- 元数据键（`_` 开头）不会被当成设备：加载时静默跳过，否则它会变成一台「谁都能挑到」的设备；
- 空表 = 全走派生；空池 = 首次部署时由真值表迁移出来（`source=migrated`）；
- 表是**读路径权威**，池是**容量权威**。两者冲突时按表归一化，多余的名额会被摘掉并打 `WARNING`。

路径两种给法：

~~~bash
# 1) 分别指
QIMEI_TABLE_PATH=/path/to/qimei_table.json
QIMEI_POOL_PATH=/path/to/qimei_pool.json

# 2) 指目录（两个文件都在这）
QIMEI_STATE_DIR=/path/to/state
~~~

首次上线先在宿主/具名卷上把池建出来，再挂进容器，不然分配结果会写进容器可写层，
重建即丢：

~~~bash
python3 -m admin.platform.marvis.core.qimei_assign --state-dir /path/to/state --sync-pool
~~~

### 4.3 生成器：本地命令 or 外部 HTTP

两条路等价，按部署形态二选一：

1. **本地命令**：`QIMEI_GEN_CMD` 指到一个生成脚本，参数里会带设备侧标识与 tag；
   容器里通常没有生成环境，这条一般只在宿主侧可用；
2. **外部 HTTP**：宿主起一个生成服务，容器按 URL 调：

   ~~~bash
   python3 -m admin.platform.marvis.core.qimei_assign --serve-generator \
     --host 127.0.0.1 --port <PORT>
   ~~~

   ~~~text
   QIMEI_GEN_URL=http://<GENERATOR_HOST>:<PORT>/qimei
   ~~~

   默认监听 `127.0.0.1`：**跨容器/跨主机时由部署方显式给 `--host`**，不要把「监听全网卡」当默认。
   仓库里的 `deploy/qimei-gen/qimei-gen.service.example` 只是骨架（账户、路径、状态目录全占位）。

生成器不可达 / 超时 / 撞重：`assign` 打 `WARNING` 后走 `shared`，**不阻塞入库**；
只有池里所有设备都满 2 个号时才会 `QimeiCapacityError`。

不配生成器也能跑：新号会走 `shared`（只满足「不超过 2 号/台」，不满足「默认独立真品」）。
这是明确的降级，不是故障 —— 但要知道自己在降级。

如果外部服务同时承担**签名**（不只是生成），接口契约见 `deploy/uskey-signer-http.md`
（`/health` + 单次请求体、字段顺序、三处数值一致性等不变量）。

## 5. 排障

### 5.1 当前账号用的是哪条来源

先看日志：每次分配都会打一行，带 `source` 和掩码后的设备串

~~~text
qimei assigned uid=<masked> source=existing|generated|shared owners=<n> qimei=<6hex>...<4hex>
~~~

- `source=existing`：账号本来就在表里（值来自真值表）；
- `source=generated`：新生成的真品；
- `source=shared`：复用了池里一台还有名额的设备；
- 池/表加载另有一行 `qimei 真值表已加载：<n> 条（含 pool 归一化）`，数字为 0 就是空表。

再看运行时实际取到的值（不打印全串）：

~~~bash
python3 - <<'PY'
from admin.platform.marvis.core import uskey
key = "<ACCOUNT_KEY>"
print("table:", uskey.qimei_table_path())
v = uskey.qimei36(key)
print("shape_ok:", len(v) == 36, "head:", v[:4], "tail:", v[-2:])
PY
~~~

判定顺序：`MARVIS_QIMEI36` 有值且长度 36 → 走 env；否则表里有这个账号 → 走表；否则派生。

### 5.2 派生值形态是否合法

~~~bash
python3 - <<'PY'
import re
from admin.platform.marvis.core import uskey
pat = r"[0-9a-f]{24}" + uskey.DEVICE_MARK + r"[0-9a-f]{8}"
v = uskey.qimei36("<ACCOUNT_KEY>")
print(len(v), bool(re.fullmatch(pat, v)), v[24:28] == uskey.DEVICE_MARK)
PY
~~~

期望：`36 True True`。形态不合法的派生值**不会**被发出去 —— 派生入口自己会抛
`ValueError`（「派生出的 qimei36 结构非法」），因为发出去等于告诉上游「这号的设备指纹坏了」。

另一条生产线上的自检：`core/uskey_local.py` 的模板固定用合成占位值，
`selfcheck()` 会校验模板里没有焊进真实身份；真夹具只从 `MARVIS_KAT_QIMEI36` 注入。

### 5.3 钩子装没装

启动日志里三行，缺哪行就少哪个能力：

| 日志 | 含义 |
| --- | --- |
| `qimei 池校验通过：设备 <n> 台 / 绑定 <m> 个（上限 2 号/台）` | 启动校验钩子已装，台账合法 |
| `qimei ORM 删除钩子已安装` | 删号回收名额已接上 |
| `qimei 真值表已加载：<n> 条（含 pool 归一化）` | 读路径拿到表（`0` = 空表，全走派生） |

反向标志（看到就知道自己在裸奔）：

- `QIMEI_VALIDATE_ON_START=0：跳过 qimei 池启动校验` —— 带病台账也会起来；
- `qimei 真值表加载失败（全走派生）` —— 路径配错，所有号都在用派生值；
- `qimei_pool 里的键不是合法 qimei36（已忽略）：...` —— 台账里有脏键，会被当成「谁都能挑」的设备；
- `qimei 自动分配模块不可用` —— 入库钩子没装上，新号不会自动分配。

池里出现 `owners=3` 时，预期行为是**进程起不来**（`QimeiPoolError`，CLI 退出码非 0）。
这不是故障，是硬约束在生效：修台账，别放宽上限。
